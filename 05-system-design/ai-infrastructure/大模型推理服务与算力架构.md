# 大模型高并发推理服务架构设计 (LLM Serving & Inference Infrastructure)

> 在 AI 时代的高并发系统设计中，大模型推理服务（LLM Serving）已成为衡量后端与系统架构师核心能力的关键考点。与传统无状态微服务不同，LLM 推理受限于 **显存带宽（Memory Bandwidth Bound）** 与 **计算吞吐（Compute Bound）** 的双重约束，核心矛盾在于如何最大化 GPU 利用率并降低 首字延迟（TTFT）与 每个 Token 延迟（TPOT）。

---

## 1. 核心瓶颈与性能指标体系

### 1.1 关键性能 SLA 指标
- **TTFT (Time to First Token)**：首字延迟。主要受 Prefill（预填充）阶段计算量决定，通常为 Compute-Bound。
- **TPOT (Time Per Output Token)**：输出每个字的时间延迟。受 Decode（解码）阶段显存带宽决定，通常为 Memory-Bandwidth Bound。
- **Throughput (Tokens/s / GPU)**：单卡并发生成的总 Token 吞吐量。
- **KV Cache 显存占用**：随着并发请求增加和长上下文扩张，KV Cache 往往比模型权重消耗更多显存。

---

## 2. 核心架构技术突破

### 2.1 PagedAttention 与虚拟显存分页
- **传统痛点**：由于序列长度不可预测，传统框架必须预先分配连续的显存空间（如预留 4K/8K tokens），导致 **内部碎片（预留未使用）** 和 **外部碎片（显存块不连续）**，有效显存利用率不足 20%~40%。
- **PagedAttention 原理**：借鉴操作系统虚拟内存分页思想，将 KV Cache 拆分为固定大小的物理块（Block，如 16 个 tokens）。
  - **逻辑块与物理块解耦**：通过 Page Table（页表）维护映射关系；
  - **按需动态分配**：新生成的 Token 仅在跨越 Block 边界时动态申请新物理块；
  - **零碎片与分支共享**：支持 Parallel Sampling、Beam Search 及 Prefix Caching 的物理块共享（Copy-on-Write），显存利用率提升至 96%+。

### 2.2 连续批处理 (Continuous Batching / Iteration-level Scheduling)
- **静态批处理缺陷**：传统 Batch 推理必须等待 Batch 中“最长序列”生成完毕才能返回，导致处理完短序列的 GPU 算力被闲置等待。
- **连续批处理实现**：
  - 在 **Iteration（Token 迭代）级别** 调度；
  - 某个请求一旦遇到 `<eos>` 结束，立即退出 Batch 并释放显存；
  - 新请求在当前 Iteration 立即插入队列中并完成 Prefill，使 GPU 算力始终保持满载。

### 2.3 投机采样 (Speculative Decoding)
- **原理**：利用轻量小模型（Draft Model，如 1B~3B）快速前向猜测多个候选 Tokens，再由主模型（Target Model，如 70B）在单次前向中进行并行验证（Parallel Verification）。
- **收益**：打破了 Auto-regressive 生成必须串行逐字解码的物理限制，在保证数学等价（无精度损失）的前提下，实现 2x ~ 3x 的解码延迟加速。

### 2.4 Prefix Caching 与长上下文复用
- 针对系统提示词（System Prompt）、多轮对话历史或少样本示例（Few-shots），在服务端自动计算哈希前缀树（Radix Tree），跨请求直接命中复用已有的 KV Cache，消除重复的 Prefill 算力开销。

## 4. 面试高频问题与回答框架

### Q1: 在高并发场景下，如何设计多租户大模型推理服务的流量隔离与配额控制？
> **回答要点**：
> 1. **两级队列机制**：基于 Token 桶算法限制每个租户的 RPM（Requests Per Minute）与 TPM（Tokens Per Minute）；
> 2. **抢占与优先级调度**：当显存水位超过高阈值（如 90%）时，挂起或抢占低优先级请求的 KV Cache 并 Offload 到 CPU 内存，优先保障高优先级 SLA；
> 3. **Prefill 与 Decode 分离部署（PD 分离）**：计算密集的 Prefill 与带宽密集的 Decode 分配在不同 GPU 节点，避免大 Prompt 的长首字计算阻塞其他请求的流式生成。

### Q2: 为什么大模型推理的瓶颈通常在内存带宽（Memory Bandwidth）而非计算算力（TFLOPs）？
> **回答要点**：
> 1. 在 Decode 阶段，每生成 1 个 Token，GPU 必须从 HBM 读取该层完整的权重参数（对于 70B FP16 模型约为 140GB）以及该请求累积的全部 KV Cache；
> 2. 计算量仅为常数级（$1 \text{ token} \times 2 \times \text{Params}$），但数据搬运量巨大，运算强度（Arithmetic Intensity）远低于 GPU 的计算能力，导致张量核心（Tensor Cores）大部分时间在等待数据搬运（Memory-Bound）。
